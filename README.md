# PanRadar · 网盘资源雷达

输入一个**作者名**或**课程名**，聚合多个网盘搜索引擎，返回**百度网盘 / 夸克网盘 / 阿里云盘 / 迅雷 / 天翼 / UC / 115** 等可下载路径（含提取码）。

零依赖：只用 Python 标准库，不需要 `pip install`。

---

## 快速开始

```bash
cd pan-radar
python panradar.py
```

浏览器会自动打开 <http://127.0.0.1:8931/>。

常用参数：

| 参数 | 说明 |
|---|---|
| `--port 9000` | 指定端口（默认 8931，被占用会自动 +1 顺延） |
| `--no-browser` | 不自动开浏览器 |
| `--no-cache` | 本次不读缓存 |
| `--selftest 关键词` | 命令行验证链路，不开浏览器，结果写入 `data/selftest.txt` |
| `--author 作者名` | 配合 `--selftest` 测试「作者 + 课程」组合查询 |

## 界面用法

1. **课程名 / 资源名 / 作者名**：主输入框，填一个就能搜。
2. **作者（可选）**：填上后会生成 `作者 + 课程名` 组合查询提升精准度，同时也会单独搜课程名和作者名。
3. **网盘筛选**：默认全选；点「只看百度/夸克/阿里」可一键收敛。
4. **深度搜索**：额外派生 `关键词+教程/课程/全集/资料/实战` 等变体，召回更多但更慢。
5. **视图切换（按资源聚合 / 按网盘分组）**：默认按资源聚合 —— 同一门课常被转存到百度 /
   夸克 / 阿里，按网盘分组时它散成三条、得自己认出是同一个东西；聚合后一份资源一块，
   块内直接列出各网盘入口，挑一个转存即可。只有百度会员的可以切「按网盘分组」。
6. **质量标签**：列表上直接标出 `[1080P] [完结] [含源码] [128集]` 这类徽章。
   原先「完整高清课」和「三条残缺搬运」在列表里长得一模一样，现在一眼能挑。
7. **提取码与复制**：提取码本身点一下即复制；单条有「复制链接+码」；每个资源块有
   「复制本组全部」（一次拿走该资源所有网盘的链接和提取码）；状态栏「⧉ 复制全部」
   导出全部结果（标题 + 链接 + 提取码，制表符分隔，可直接贴进表格）。
8. **⟳ 再挖一次**：跳过缓存重新查询，新结果**并入**已有缓存（不是覆盖），所以要找的冷门资源，
   多按几次会越挖越全。
9. **💡 顺藤摸瓜**：搜作者名往往只出几条 —— 因为资源是按**课程名**索引的。搜完后系统会从
   已搜到的标题里认出「除了搜索词之外的名字」并做成按钮，点一下换它再搜。
   实测：搜「风间影月」只出 2 条 → 认出「Java高级工程师」→ 点一下变成 42 条。
10. **导出**：右上角可导出 Markdown / CSV（含网盘类型、标题、链接、提取码、日期）。

## ⚠️ 两条最关键的经验（改代码前务必先读）

### 1. 绝对不要用 `res=merge`，必须用 `res=all`

这是本项目命中率的**头号决定因素**。同一个关键词实测：

| 请求方式 | 返回 | 耗时 |
|---|---|---|
| `res=merge`（合并后结果） | **2 条** | 5s |
| `res=all`（原始 results，含每条自己的 links[]） | **324 条 / 3048 个链接** | 8s |

`merge` 模式只吐出「已归类且去重后」的极少数结果，会丢掉 **97%** 的命中。
搜「Java高级工程师」时 `merge` 只给 2 条，`all` + 本地过滤给 **61 条**，其中就包含
「[慕课网]Java高级工程师(风间影月)」——用户真正要找的东西。

**所以：拿 `results[]`，自己在本地做相关度过滤。**

### 2. 噪声必须用「最长公共子串」过滤，不能用「命中词数」

盘搜源的模糊匹配很脏：搜「风间影月」会返回《人间风月录》《一饭封神》这类
只沾一个字的无关资源；搜「Vibe Coding 一人团队项目开发实战」会返回一堆网剧。

用「命中词数」判定挡不住（单字也算命中）。本工具用**最长公共子串占查询串的比例**：

```
「风间影月」 vs 「慕课网-Java高级工程师(风间影月)」 -> 4/4 = 1.00  ✓ 保留
「风间影月」 vs 「擦边短剧：人间风月录」           -> 1/4 = 0.25  ✗ 丢弃
```

只沾到 1 个字的（`LCS < 2`）直接记为 0 分。低于 `drop_below`（默认 0.34）的结果不返回；
0.34–0.6 之间的标记「低相关」，但仍可能是有用的合集包。

### 3. 上游 `title` 字段被字节截断，完整名字在 `content` 的「名称：」里

这是「明明搜到了课程，界面却显示成『马老师的』」的根因。同一条结果的两段：

```
title   : '马老师的'                        ← 被按字节硬截断
title   : '慕课网-体系课-Java高级工程师('      ← 截断后还挂着一个配不上的左括号
content : '名称：马老师的Java高级工程师 就业班 描述：本课程由资深Java专家马老师授课…'
```

**规则**：把 `content` 里「名称：xxx」抠出来，若 title 归一化（去空格/括号/标点）后是它的前缀、
且只少 ≤25 个字 —— 那必然是截断，用完整名替换。多出几十个字的不算（那是标题里塞了整段描述，
例如「IT培训教程合集【网易云课堂…23.8G】…」，用了反而更糟）。

同时裁掉截断留下的悬空括号 —— 只在左括号出现在结尾 12 字内**且不配对**时才裁，
否则会误伤「超级工程 (2012) 1080P」。

## 只搜到几条？用「顺藤摸瓜」

**资源是按课程名索引的，不是按作者名。** 所以搜作者名常常只出几条。

搜完作者名后，工具会从已搜到的标题里认出「除了搜索词之外的名字」，做成蓝色按钮放在状态栏下方，
点一下换个词再搜。实测：

```
搜「风间影月」           -> 2 条（只有 pansou.app 收录）
  💡 认出「Java高级工程师」
点一下再搜              -> 42 条（同课程在 TG 频道里被分享了几十次）
```

判定规则：只从**高相关**（rel ≥ 0.6）的标题里挖；词组归一化后要 ≥5 字（否则会挖出
「就业班」「合集」这类没有区分度的泛词）；先按出现频次排，再按长度排；剥掉
「095.」这类序号前缀；互相包含的只留一个。

## 同一份资源怎么跨网盘聚到一起

搜到 42 条 **≠** 有 42 份资源。同一门课常被转存到百度 / 夸克 / 阿里，而去重键是
「网盘类型 + 分享 ID」，所以它们不会被合并 —— 得靠**标题相似度**聚类。

用的是 **bigram（字符二元组）Dice 系数**，不是编辑距离：

```
「尚硅谷Redis分布式缓存」 vs 「尚硅谷MySQL高级」
  编辑距离：只差 4 个字符，会判成很像               ✗ 误聚
  bigram  ：交集只有「尚硅」「硅谷」，Dice = 0.29   ✓ 不聚
```

中文没有分词库，编辑距离对短标题过于宽松；bigram 能看出两个词实际共享了多少内容。
判定顺序：先看长度差（超过 60% 直接排除）→ 再看是否互为连续子串（覆盖绝大多数
「课程名 + 【完结】【1080P】」这种后缀差异）→ 最后用 Dice ≥ 0.75 兜底。
每个簇最多记 6 个 key，防止簇变大后两两比较的次数失控。

## 质量标签是怎么抽的

纯正则，零网络请求，全部来自上游本来就返回的 `title` 和 `content`：

| 类别 | 命中示例 | 展示 |
|---|---|---|
| 清晰度 | `4K` `2160P` `1080P` `720P` `高清` | 绿 / 灰 |
| 状态 | `完结` `完整版` ／ `更新中` `连载` | 绿 / 橙 |
| 内容 | `源码` `课件` `讲义` `面试题` `笔记` `PDF` | 绿 / 灰 |
| 规模 | `128集` `45讲` `30期` | 灰 |
| 便利 | `无密` `免提取码` | 绿 |

同一类别只取第一条命中的规则（避免「1080P 高清 超清」刷一排同义标签），
但「有没有源码」和「有没有课件」是两件独立的事，所以拆成不同类别都保留。

**坑**：裸的「资料」二字太宽松，几乎每条标题都沾，会误标成「含资料」；
必须收紧成 `附资料|含资料|配套资料|资料包`。

## 结果是怎么排序的

每条结果会带一个 `匹配 xx%`（即上面的 LCS 相关度）和一个综合 `score`：

- 查询词完整命中标题：+55，并按「命中字数 / 标题长度」加权（短标题更精准）
- 按最长公共子串比例给分
- 相关度加权：×30
- 网盘优先级（可在 `config.json` 的 `cloud_priority` 调整）：夸克 > 百度 > 阿里 > UC > 迅雷 …
- 时效性：越新的分享加分越多，30 天后衰减到 0
- 带提取码：+4；有文件体积信息：按体积小幅加分
- 超长乱码标题：-6

去重按「网盘类型 + 归一化分享 ID」进行，同一资源被多个源收录时只保留一条，
并合并提取码、**取信息量最大的标题**（踩过坑：早先按「更短更干净」合并，
把「马老师的Java高级工程师就业班」换成了别的源给的「马老师的」，课程名整个丢失）。

## 数据源配置

`config.json` 在首次运行时自动生成，**升级代码后会自动迁移**（你自加的源会保留）：

```json
{
  "config_version": 4,
  "sources": [
    { "name": "PanSou · so.252035.xyz", "type": "pansou",
      "search_url": "https://so.252035.xyz/api/search", "enabled": true },
    { "name": "PanSou · pansou.app", "type": "pansou",
      "search_url": "https://pansou.app/api/search", "enabled": true },
    { "name": "混合盘搜索", "type": "disksearch_slim",
      "search_url": "https://hunhepan.com/open/search/disk",
      "referer": "https://hunhepan.com/search", "pages": 2, "enabled": true },
    { "name": "Misoso 夸克搜索", "type": "disksearch",
      "search_url": "https://www.misoso.cc/v1/search/disk",
      "referer": "https://www.misoso.cc/search",
      "origin": "https://www.misoso.cc", "enabled": true },
    { "name": "自建 PanSou (Docker)", "type": "pansou",
      "search_url": "http://127.0.0.1:8888/api/search", "enabled": false }
  ]
}
```

支持三种源类型：

| type | 协议 | 说明 |
|---|---|---|
| `pansou` | `GET /api/search?kw=&res=all&src=all` | PanSou 实例。内部聚合 **几十个 TG 频道 + 若干插件**，是命中的主力 |
| `disksearch` | `POST` 完整参数体（`page/q/user/exact/format/share_time/size/type/exclude_user/adv_params`） | misoso 系 |
| `disksearch_slim` | `POST` **只有** `{q, page, size}` | hunhepan 系。**多传任何字段都返回「参数错误」** |

### 踩过的坑（省得你重踩）

- `disksearch_slim` 接口**忽略 `size`**，每页固定 10 条，只能靠 `page` 翻页；`total` 可达 300，
  所以配置里有 `pages` 字段（默认翻 2 页，翻太多会被 429）。
- `hunhepan.com` 限流较狠，被 429 后会冷却 10 分钟，期间状态栏显示「冷却中，本次跳过」，属正常现象。
- `qkpanso.com` / `kuake8.com` 与 hunhepan 同源，但前者要签名校验（`code=414 请求校验失败`）、
  后者超时/400 —— 已试过，暂不可用。
- 传 `plugins` 参数会导致 400/403/超时，不要传。
- `channels` 参数只能**收窄**结果（指定单个频道 `merged` 反而更多，但总量更少），不能扩展覆盖，没意义。
- 搜狗/Bing/360 兜底实测几乎没有价值：中文索引里基本没有网盘分享页，
  360 偶尔能捞到 1 条，Bing 的链接是 base64 重定向且内容为 JS 渲染。不要走这条路。
- 微信文章 / 知乎 / 贴吧 / 掘金 等平台页同样捞不到（需 JS 渲染或登录），已实测。

### 强烈建议自建数据源

公共实例的稳定性和限流不可控（同一关键词两次查询结果可能差很多，也可能某个源直接超时）。
自建只需一条命令：

```bash
docker run -d --name pansou -p 8888:8888 -v pansou-cache:/app/cache \
  ghcr.io/fish2018/pansou:latest
```

然后把 `config.json` 里 `自建 PanSou (Docker)` 的 `enabled` 改成 `true`。
主源会跑全部关键词变体，备用源只跑前几个，总量由 `max_requests` 封顶。

## 空结果自动降级（分词）

搜不到的时候不用手动换词。逻辑是：

1. 先用完整短语（含去空格变体）搜全部源；
2. 如果**相关结果为 0**，自动把输入拆成独立词（如 `一人公司 AI产品创造营` → `一人公司`、`AI产品创造营`）再各搜一遍；
3. 界面会用黄色提示「已自动降级分词」，并列出实际用的查询词。

## 出错时你能看到什么

前端不裸用 `(await fetch()).json()` —— 那在响应体为空时会抛一句用户完全看不懂的
`Unexpected end of JSON input`。统一走 `apiGet()`：先读文本、判空、判 HTTP 状态、再解析，
每种故障给一句能照着做的话。

| 实际发生了什么 | 以前 | 现在 |
|---|---|---|
| 服务在重启 / 连接被重置（**最常见**） | `Unexpected end of JSON input` | 「后端返回了空响应。服务可能正在重启，请稍等几秒重试。」+ **自动重试一次** |
| 后端返回了 HTML 错误页 | 同上，无信息 | 「后端返回的不是合法 JSON（HTTP 500）。内容开头：…」 |
| 服务没起来 | 同上，无信息 | 「无法连接后端服务。请确认 panradar.py 仍在运行，然后刷新页面。」 |
| 上游太慢 | 一直转圈，像卡死 | 「请求超时（超过 240 秒）…请重试，或点 ⟳ 再挖一次。」 |
| 搜索耗时较长 | 一片空白，用户以为死了去刷新 | 每秒更新「已等待 N 秒…（数据源多时较慢，请稍候）」 |

错误块里带一个 **「重试」按钮**，不用重新输关键词。

> **改了 `web/index.html` 之后必须强刷页面**（`Ctrl+F5`）。浏览器缓存的是旧 JS，
> 不刷新的话服务端已经是新版、前端还在跑旧代码。

## 工程实现要点

- **显式绕过系统代理**：`urllib.request.ProxyHandler({})`。本机代理会破坏到搜索源的 TLS 连接（表现为 `Tunnel connection failed: 502` / `WinError 10054`），这是本工具能跑通的前提。
- **重试与退避**：`400/401/403/414/5xx` 退避后重试；**`429` 不重试**（对端已经记账，退避再打只会把这台机器钉得更死，实测白等 9 秒），直接交给分级冷却。`max_concurrency` 控制并发，默认 6。
- **失败源分级冷却**：`429/403` 冷却 10 分钟，其它错误 2 分钟，期间跳过该源。全部源都在冷却时仍放行全部，避免无源可用。
- **整体超时上限 35s**：单源与整批都按 35s，避免一个源挂起拖死整次搜索；超时的源在状态栏单独标红，其他源结果照常返回。
- **标题处理两道工序**：先 `_clean_title` 洗掉 emoji / 营销前缀 / 话题标签并裁掉截断的悬空括号，再 `_enrich_title` 用 `content` 的「名称：」字段把被字节截断的标题补全。
- **两级缓存**：`data/panradar.db`（sqlite）缓存每个「源 + 关键词」的原始结果，默认 30 分钟有效；界面右上角「清缓存」可手动失效。缓存 key 带命名空间前缀（`CACHE_NS`），协议变更时改它即可让旧缓存自动失效。**缓存按 url 去重后并入而非覆盖**，所以「再挖一次」能累积。
- **容错业务码**：misoso 用 `code=417`、hunhepan 系用 `code=0` 表示「没有搜索结果」，按空结果处理而不是报错。
- **HTTP 服务**：`ThreadingHTTPServer`，接口只有 `/api/search`、`/api/meta`、`/api/history`、`/api/export`、`/api/cache/clear`。
- **响应绝不返回空 body**：`do_GET` 外层包了总异常捕获，任何抛错都回一个 `{"ok": false, "error": ...}` 的 500；
  `_json` 用 `default=str` 兜底，避免某个字段混进 `set`/`datetime` 就把整个响应炸掉。
  **这条必须守住** —— 异常冒泡出 `BaseHTTPRequestHandler` 会直接关连接，前端只收到 0 字节，
  表现成一句毫无线索的 `Unexpected end of JSON input`。
- **日志必须行缓冲**：`main()` 开头 `sys.stdout.reconfigure(line_buffering=True)`，启动时也建议带 `-u`。
  输出被重定向到文件时 Python 默认块缓冲（8KB），日志会一直卡在内存里 —— 本项目就出现过
  `data/_srv.log` 长期 0 字节、服务端异常完全无从查证的情况。
- **测试**：`data/_title_test.py`（标题补全 16 例）、`data/_topic_test.py`（顺藤摸瓜 9 例）、
  `data/_feat_test.py`（质量标签 + 跨网盘聚类 32 例）、`data/_ui_test.js`（带 DOM 桩的前端集成测试 64 例）、
  `data/_api_test.py`（后端响应健壮性 12 例）、`data/_jscheck.py`（前端语法）。
  改标题 / 相关度 / 建议词 / 请求层逻辑后请跑一遍。

```
   ├─ _deploy_fc.py         # 用 OpenAPI SDK 建/更新 FC 服务、函数、HTTP 触发器
   ├─ _deploy_oss.py        # 建桶、开静态托管、上传 web/ 并注入 API 地址
   └─ fc/_build_fc_code.py  # 打 code.zip（含 bootstrap）
```

## 线上部署（OSS 静态前端 + FC 聚合层 · 香港）

已经跑通并在线运行的一套，不用 Docker、不用 Serverless Devs：

| 组件 | 地址 |
| --- | --- |
| 前端 | https://panradar-ydtgo-hk.oss-cn-hongkong.aliyuncs.com/ |
| API | `https://panradar-panradar-svc-neqacybvqm.cn-hongkong.fcapp.run` |

架构上前端只调 FC 的 `/api/*`：`pansou.app` 无 CORS、`misoso`/`hunhepan` 是 http 会被混合内容拦截，
**多源聚合只能由服务端完成**，这部分算力放在 FC；静态页面放 OSS，两者都用香港地域。

完整步骤（凭证、打包、部署、验证、注意事项）见 **[deploy/fc/README.md](deploy/fc/README.md)**，简版：

```bash
export ALIBABA_CLOUD_ACCESS_KEY_ID=...
export ALIBABA_CLOUD_ACCESS_KEY_SECRET=...
pip install alibabacloud_fc_open20210406 alibabacloud_tea_openapi alibabacloud_tea_util oss2

python deploy/fc/_build_fc_code.py   # 打 code.zip
python _deploy_fc.py                 # 部署 FC，打印公网地址
# 把地址填进 _deploy_oss.py 的 FC_URL
python _deploy_oss.py                # 部署 OSS 前端并注入 API 地址
```

几个线上才体会到的点：

- **首次搜索约 100 秒**（冷启动 + 4 源并发 + 重试），FC `timeout: 120s` 刚好兜住。
- **接口参数是 `main` 不是 `q`**：`/api/search?main=风间影月`，用错会回 `请输入课程名或作者名`。
- **缓存随实例冷启动清空**（落在 `/tmp/panradar`），「再挖一次」的累积只在 warm 实例内有效。
- 改了 `web/` 之后必须 `Ctrl+F5` 强刷，否则前端还在跑旧 JS。
